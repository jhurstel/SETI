# CLAUDE.md

Adaptation numérique du jeu de société **SETI** (Iello) en TypeScript + React (Vite). Projet solo, code et commentaires en **français**.

- Dépôt GitHub : https://github.com/jhurstel/SETI (remote `origin`, **public**), branche unique `main`. **Toujours faire `git pull` avant d'analyser ou de modifier le code** (le travail se fait sur plusieurs machines).
- Règles officielles : `public/docs/seti-rules-fr.pdf`, FAQ : `public/docs/SETI-FAQ-FR.pdf` (référence pour toute question de règle ; accessibles dans le jeu par le bouton Documentation).
- Documentation du jeu : `public/docs/documentation.md` (affichée par le bouton 📖 à côté des paramètres) : la tenir à jour quand une règle, une action, une interaction ou un poids des robots change. Une ligne `{{glossaire}}` y insère le glossaire des symboles (`ui/components/SymbolGlossary.tsx`, vraies icônes de l'interface) : y ajouter tout nouveau symbole.
- `gh` CLI n'est pas installé sur la machine ; Git utilise HTTPS.

## Commandes

```bash
npm install          # dépendances (Node >= 20.19)
npm run dev          # lance le jeu (serveur Vite, alias : dev:ui)
npm run typecheck    # tsc --noEmit (0 erreur attendue)
npm run lint         # ESLint (0 erreur attendue ; les warnings = dette connue)
npm test             # Jest (test/*.test.ts, ts-jest)
npm run test:coverage # Jest + couverture du moteur (hors ui/, rapport HTML dans coverage/)
npm run test:e2e     # Playwright (e2e/*.spec.ts) : tour d'un joueur humain dans un vrai navigateur
npm run check        # typecheck + lint + tests + build — à lancer avant chaque commit
npm run tune:ai -- tune 140   # réglage SPSA des poids des robots (tools/spsa/README.md) ; compare <a.json|default> <b.json|default> <graines> pour valider
npm run build        # typecheck puis vite build (→ dist/)
npm run server       # serveur du jeu à distance : server:build (esbuild → server/build) puis server:start (PORT=8787, SETI_DATA_DIR=server/data, ALLOWED_ORIGINS)
```

La CI (`.github/workflows/ci.yml`) exécute typecheck, lint, tests et build à chaque push sur `main`, et les tests de bout en bout dans un job séparé (`e2e`). En local sous Windows, Playwright utilise le Chrome installé (`PW_CHANNEL` pour en choisir un autre ; Edge est bloqué sur certains postes).

## Règles de travail

- **Séparer le moteur de l'affichage.** Toute règle du jeu (coûts, gains, validations, effets de carte, décisions des robots) vit dans le moteur (`core/`, `systems/`, `actions/`, `ai/`), en TypeScript pur, sans React. L'interface (`ui/`) ne fait qu'appeler le moteur, appliquer l'état renvoyé, afficher l'historique, les toasts et les fenêtres. Si un handler de l'UI calcule une règle, la déplacer dans le moteur avant d'y ajouter quoi que ce soit.
- **Tester chaque opération du moteur.** Toute nouvelle opération ou toute correction du moteur s'accompagne d'un test Jest dans `test/` (avec une vraie partie via `createTestGame()`), qui vérifie le résultat et que la partie reçue n'est pas modifiée. Un bug corrigé reçoit un test de non-régression ; un bug connu non corrigé, un `test.failing`.
- **Les robots passent par les mêmes opérations que le joueur humain** (pas de copie des règles dans `ai/`), et chaque opération de robot est testée. Une commande du joueur que la session traite elle-même (pas de déplacement, défausse pour action gratuite…) a son opération dans le moteur (`InteractionChoices.moveProbe`, `CardSystem.discardFromHandForFreeAction`), appelée par `GameSession` et par les robots ; un choix du joueur sur une interaction passe par `InteractionChoices`, robots compris (achat : `acquireCard`, recherche : `acquireTech`, réservation de mise en place : `reserveCards`).
- Lancer `npm run check` avant chaque commit.

## Architecture et conventions

- **Moteur indépendant de l'UI** : `core/`, `systems/`, `actions/` et `session/` sont du TS pur. **Toute modification de la partie passe par `GameSession.dispatch(game, playerId, command)`** (dans l'UI : `useGameSession().dispatch`, via `run(command)` dans `BoardUI`) : la session vérifie qui joue et ce qui est permis (tour, interaction en cours et son joueur, règles des actions gratuites), applique la règle, résout les interactions automatiques et celles des robots, termine les tours (paliers compris, `game.endingTurn`) et renvoie les entrées d'historique et les annonces. Les robots passent par `GameSession.applyRobotStep`. L'UI garde seulement ses modes de sélection (défausse de fin de manche, échange de cartes, cartes cochées), les fenêtres de confirmation et les animations ; elle peut lire les systems pour afficher (coûts, cases jouables), jamais pour modifier la partie.
- **État immuable** : les systems prennent un `Game` et renvoient `{ updatedGame, historyEntries, ... }` **sans jamais modifier la partie reçue**. Dans le moteur, toute fonction qui modifie l'état commence par `cloneGame(game)` (`src/core/cloneGame.ts`, copie profonde ; à utiliser aussi dans l'UI plutôt que `structuredClone`). Pour la performance (la copie fait l'essentiel du temps des robots), les effets des cartes et les effets et bonus des technologies sont **figés et partagés** entre les copies : ne jamais les modifier (une modification lève une `TypeError`) ; les champs variables d'une carte (`ownerId`, `isRevealed`, `completed`…) restent copiés. Pas de copie superficielle `{ ...game }` suivie de mutations : c'était la source de bugs d'undo. `test/Immutability.test.ts` vérifie cette règle.
- **Historique** : `HistoryEntry { message, playerId, sequenceId, previousState }`. `sequenceId` regroupe les entrées d'une même action et sert à l'undo. Le journal est tenu par `SessionJournal` : la première entrée de chaque commande garde l'état d'avant (file d'interactions comprise), seulement depuis le début de l'avant-dernier tour de chaque joueur humain (on peut encore revenir au tour qu'on vient de finir, robots compris) ; `undoLast` revient au début de la séquence, `undoTurn` au début du tour. Le moteur ne garde pas d'instantanés (l'ancien `game.history`, jamais utilisé, faisait passer l'état de 170 Ko à plus de 10 Mo en fin de partie). Les messages sont en français et affichés au joueur. Un passage qu'un seul joueur a le droit de lire (nom d'une carte piochée face cachée : pioche, achat dans la pioche, échange, bonus, réservation, carte Alien de la pioche, cartes de découverte) s'écrit `privateText(propriétaire, texte)` (`core/historyText.ts`) : l'historique local l'affiche (`revealText`), `viewEntries` (`session/PlayerView.ts`) le retire pour les autres joueurs. Tout nouveau message qui nomme une carte cachée doit l'utiliser (`test/PrivateHistory.test.ts`). La première entrée de l'action principale d'un tour porte `mainAction` (posé par `GameSession`, joueur et robot, gardé par la sauvegarde) ; `core/historyTimeline.ts` découpe l'historique en manches et en tours pour la barre de progression (`ui/components/HistoryProgressBar` : fenêtre de fin de partie, carte « Continuer » de l'accueil).
- **Interactions multi-étapes** : union discriminée `InteractionState` (`types.ts`). L'interaction en cours et la file sont dans la partie (`game.interaction`, `game.pendingInteractions`, gérées par `InteractionQueue` : plusieurs gains à choix forment un menu, les résolutions de secteur passent en dernier). Pour en ajouter une : variant dans `InteractionState`, libellé dans `getInteractionLabel`, fonction dans `InteractionChoices`, genre de `Choice` (`session/commands.ts`) et cas dans `GameSession.choose`, cas dans `AIController.processSingleInteraction` pour les robots, puis le clic dans l'UI (`choose(...)`).
- **Cartes** : CSV `;` avec les colonnes `Id;Nom;Type;Texte;Action gratuite;Couleur scan;Revenu;Cout;Gain;Contrainte`. `Gain` et `Contrainte` encodent les effets (`1 Sonde + 1 Média`, `GAIN_ON_VISIT:jupiter:data:1`, `VISIT_PLANET:mars:4`…), parsés dans `DataLoader`. Modifier une carte = modifier le CSV dans `public/cards/`.
- **Effets de carte** : `CardEffect.value` est de type `CardEffectValue` (nombre, booléen, chaîne de mission, `EffectAmount` ou `Bonus`). Le lire avec les accesseurs de `core/cardEffects.ts` (`effectNumber(effect)` pour un calcul, `effectString` pour une mission `GAIN_IF_…`, `effectAmount<Scope>` pour quantité + portée, `effectBonus` pour des gains multiples), jamais avec `effect.value` brut dans une opération.
- **Vérifications** : un joueur inconnu est une erreur de programmation, `requirePlayer(game, id)` (`core/players.ts`) lève une exception plutôt que de renvoyer une valeur par défaut. Les vérifications `canX` renvoient un `RuleCheck<'canX'>` (`types.ts`) : un refus porte toujours sa raison, affichée telle quelle. Pas de garde (`|| []`, `if (!x)`) sur un champ que les types garantissent.
- **Joueurs** : `type: 'human' | 'robot'`, niveau du robot dans `player.aiDifficulty` (absent = EASY). L'humain est piloté par l'UI. Les robots sont gérés par `AITurn.playStep` / `AITurn.endTurn`, qui s'appuient sur `AIBehavior` et `AIController` ; le hook `useAITurn` appelle une étape toutes les 1,5 s, calculée dans un Web Worker (`ai/aiWorker.ts`, `ui/hooks/aiWorkerClient.ts` ; repli sur le fil principal si le Worker est indisponible) pour ne pas figer l'interface ; l'état du générateur aléatoire (`game.rngState`) fait l'aller-retour avec la partie, et l'étape est appliquée par `GameSession.applyRobotStep` (le robot attend tant qu'une interaction attend un humain : `GameSession.robotCanPlay`). Toute logique de robot va dans `AITurn` (moteur), pas dans le hook. `test/AITurn.test.ts` joue des parties complètes entre robots : c'est le test de non-régression global du moteur.
  - **Niveaux** : EASY (Débutant) simule chaque action principale, sans préparation, et en tire une au hasard parmi les 3 meilleures qui améliorent sa position (`AITurn.chooseEasyMainAction`), sinon il passe ; il compare 2 tirages pour ses choix aléatoires (`AIBehavior.choiceSamples`) et garde/défausse ses cartes selon leur coût jouable. Ses actions gratuites restent occasionnelles et au hasard. MEDIUM simule chaque action principale et chaque action gratuite avec le vrai moteur (`AITurn.chooseBestMainAction`, `tryBestFreeAction`), note la position obtenue avec `AIEvaluator.evaluate` (PV + ressources et potentiel pondérés par les manches restantes) et garde la meilleure ; il passe quand aucune action n'améliore sa position. EXPERT joue comme MEDIUM, mais son évaluation ajoute les points du décompte final déjà acquis (`ScoreManager.calculateFinalScore` : tuiles objectif, cartes Fin de partie ; poids `endGameBefore` avant la dernière manche, 100 % pendant) : sur 72 parties contre MEDIUM, 61 % de victoires et environ +11 PV en moyenne (mesure antérieure à la correction de la recherche de technologie des robots et au dernier réglage des poids, à refaire). Pistes essayées sans gain : anticiper le coup suivant (plus lent, surévalue l'épargne), retrancher la position du meilleur adversaire. Comparer deux niveaux demande au moins une cinquantaine de parties (scores très dispersés). Les poids de `AIEvaluator` (`DEFAULT_WEIGHTS`, partagés par tous les niveaux) ont été réglés ensemble par SPSA en faisant jouer des Experts entre eux, à 2 et 3 joueurs (dont le facteur de dernière manche `lastRoundFactor` et le seuil des actions gratuites `freeActionMinGain`) ; dernier réglage : 140 itérations de 48 parties en miroir (mêmes graines, sièges échangés), paramètres en log, moyenne des 70 dernières itérations, puis validation sur 404 parties à graines neuves : +6,6 ± 1,5 PV et 229 victoires contre 173 face aux poids précédents (banc de réglage : `tools/spsa/`, `npm run tune:ai` ; il compile un worker avec esbuild et fait jouer les parties en parallèle, environ 2 s par partie à 2 joueurs) ; `AIEvaluator.weightOverrides` permet de donner d'autres poids à un joueur pour ce genre de comparaison (vide en jeu). Pour les interactions à choix aléatoire, `AIController` compare 4 tirages et garde le meilleur. Pour renforcer l'IA, ajuster d'abord les poids de `AIEvaluator`.
- **Interactions automatiques** (`TRIGGER_CARD_EFFECT`, `RESOLVING_SECTOR`, `DRAW_AND_SCAN`, `CLAIMING_MISSION_REQUIREMENT`) : une seule implémentation, `InteractionResolver.resolve`, appelée par `GameSession` (dès qu'une telle interaction arrive en tête de file) et par `AIController` (robots). Ne pas réimplémenter ces règles ailleurs. De même, toutes les interactions à choix passent par `InteractionChoices` : cartes (`acquireCard`, `selectScanCard`, `reserveCards`, `discardForSignals`, `playExertienCard`), sondes (`chooseMediaOrMove`, `removeProbe`, `takeSpecimen` et `specimenPlanets`), observations (`observation2`, `observation3`, `observation4`), ainsi que `placeLifeTrace`, `acquireAlienCard`, `placeObjectiveMarker`, `acquireTech` (technologies autorisées par `TechnologySystem.acquirableTechs`, colonne d'ordinateur, `noTileBonus`), `placeBonusProbe` (placements restants dans `nextInteraction`), `claimCentaurienReward` (palier `markerId`), `chooseMissionRequirement`, `chooseBonusAction`, `applyScanFollowUp` (signaux « secteur d'une sonde » d'une même carte, `ScanSystem.scanFollowUp` : tous dans le même secteur, sauf la carte 30 : une sonde par signal), `noteDiscovery` pour annoncer une découverte d'espèce ; déplacements gratuits consommés : `ProbeSystem.freeMovementsUsed` ; défausse en passant : `CardSystem.cardsToDiscardAtPass`, vérifiée par `PassAction`) : l'UI fournit le choix du clic, le robot celui de sa simulation ou de son tirage ; une nouvelle interaction à choix y ajoute sa fonction (avec son test), plutôt qu'une règle dans un handler ou dans `AIController`. Une fonction qui laisse une suite (cartes, placements ou déplacements restants) la renvoie dans `nextInteraction`. Une interaction destinée à un autre joueur porte son `playerId` ; pendant le tour d'un robot, celles destinées à un humain entrent dans la file de la partie (`AIController` → `AITurn` → `GameSession.applyRobotStep`) et seul ce joueur peut y répondre ; une interaction destinée à un robot est résolue par `AIController` dans la session. Pour placer automatiquement une trace de vie, utiliser `SpeciesSystem.placeLifeTraceAuto` (ordre de `lifeTraceOptions` : couleur manquante d'une espèce non découverte, puis n'importe quel emplacement libre de la piste d'une espèce découverte, plus l'emplacement infini suivant si l'espèce en a (`SpeciesSystem.hasInfiniteSlot` : ni Mascamites ni Exertiens), puis emplacements excédentaires) ; les robots (tous niveaux) simulent chaque emplacement et gardent le mieux évalué (`AIController.bestLifeTracePlacement`), l'évaluation comptant la carte Alien promise par une 1re trace (`discoveryClaim`) et les cartes Alien en main (`alienCard`). L'évaluation compte aussi les secteurs en cours de remplissage (`sectorProspects` : 1 Média si présent, part du bonus de couverture si majoritaire, selon le remplissage) ; mesuré neutre sur la force de jeu (96 parties, −0,1 ± 3,3 PV). Exertiens : l'évaluation (tous niveaux) retire la pénalité de danger attendue (10 % du score final estimé, pleine si le joueur est le plus exposé, réduite par point d'écart : `dangerPenalty`, `dangerMarginDecay`, `minPointsPerRound`) et compte les PV des cartes Exertiens jouées (pleins si la condition est remplie, sinon × `exertienStepChance` par étape manquante, via `ScoreManager.exertienCardProgress`) ; à un palier, le robot simule chaque carte et le renoncement (`AIController.bestExertienCard`). Sur 20 parties à 3 Experts contre l'ancien choix (carte la moins dangereuse) : danger moyen 7,6 au lieu de 11,1, 1,1 carte jouée par joueur au lieu de 1,5, mais toujours peu de conditions remplies (18 %).
- **Logique métier hors de l'UI** : un handler de `BoardUI` ne fait qu'envoyer une commande (`run`, `choose`) ; une règle qui manque va dans le moteur (systems, actions, `InteractionChoices`, `GameSession`), avec son test.
- **Cartes Exertiens** : stockées dans `player.cards`, mais elles ne sont **pas en main** (règles et FAQ Q40). Elles ne comptent pas dans la limite de 4 cartes et ne peuvent être ni défaussées, ni réservées, ni jouées normalement. Pour tout ce qui concerne « la main » (défausse, passe, choix de l'IA…), utiliser `CardSystem.getHandCards(player)`. Une carte Exertien se joue uniquement à un palier Exertien (`SpeciesSystem.playExertienCard`), une fois par joueur et par palier (`player.claimedExertienMilestones`). À la découverte des Exertiens, chaque joueur qui a un marqueur de découverte peut en jouer une tout de suite (palier 0, `CHOOSING_EXERTIEN_CARD` avec son `playerId`) ; au 2e palier, jouer sa carte coûte 1 crédit (`SpeciesSystem.exertienCardCost`, choix proposé seulement si le joueur peut payer). Toute découverte d'espèce passe par `SpeciesSystem.discoverSpecies` (plateau et `species.discovered`, cartes, mise en jeu propre à l'espèce, choix ouverts), que ce soit par une trace de vie ou par un palier neutre ; elle produit l'annonce `DISCOVERY_NOTICE`, que `GameSession` renvoie nommée (`discoveryNotice(espèce)`, relue par `noticedSpecies`) : bande « Nouvelle espèce » de l'interface (`ui/components/Announcement`, qui sert aussi à l'annonce de début de tour). Le contour du système solaire et le toast sont toujours à la couleur du joueur qui a la main (`--turn-color` sur `.seti-root-inner`), le plateau joueur à celle du joueur affiché (`--board-color`). Pendant le tour d'un autre joueur, l'interface ne voile pas le plateau : le cadre du système solaire s'illumine (`.seti-waiting`), plateau consultable ; en local, `run` refuse une commande au nom d'un robot. Les choix ouverts en fin de tour remontent en liste (`TurnManager.finishTurn` → `pendingInteractions`, `AITurn.endTurn` → `humanInteractions`).
- **Missions déclenchables** : un déclencheur propose tous les cercles non recouverts qu'il remplit, dans l'ordre choisi par le joueur (règles, FAQ Q28 ; un seul par récompense identique sur une carte, 129) (`CardSystem.processMissionBuffs`, `fulfillableRequirementIds`) ; « toute trace de vie » = `GAIN_ON_ANY_LIFETRACE` ; une trace « quelconque » prend la couleur de l'emplacement choisi. Un déclencheur ne recouvre qu'un cercle, toutes cartes confondues, au choix du joueur : en recouvrir un vide les autres cercles du même déclencheur (`Mission.fulfillableTriggers`, `InteractionResolver.claimMissionRequirement`) ; ceux d'un autre déclencheur (2e technologie acquise…) restent réalisables. Pendant son tour, le joueur clique sur un cercle surligné (`CLAIM_MISSION`) ; hors de son tour, `GameSession.offerTriggeredMissions` lui propose aussitôt les cercles devenus réalisables (`CHOOSING_MISSION_REQUIREMENT`, `InteractionChoices.chooseMissionRequirement`, renoncement possible ; robots : `AIController.bestMissionRequirement`) (`test/MissionTriggerOffTurn.test.ts`).
- **Spécimens Mascamites** : à la découverte, 3 jetons face cachée sur Jupiter, 3 sur Saturne : un joueur les voit en choisissant un spécimen à prélever ou étudier (`SpecimenModal` ; robots : `AIController.bestSpecimen`), puis il les voit seul (`planet.mascamiteSeenBy`, `SpeciesSystem.canSeeSpecimens`, utilisé par `viewFor` et l'interface) ; le spécimen d'une capsule n'est visible que par son propriétaire ; le 7e face visible sur la 3e case de la piste bleue (`MASCAMITE_BOARD_SPECIMEN_SLOT` : sa récompense devient le gain de la case). Prélever un spécimen (cartes « … et prélevez un spécimen », sur Jupiter, Saturne ou leurs lunes) le place dans une **capsule** : une `Probe` à l'état `ProbeState.CAPSULE` portant `specimen`, posée sur la case de la planète d'origine. Elle se déplace et se comporte comme une sonde (énergie ou déplacements, défausse d'une carte Déplacement : `ProbeSystem.hasMovablePiece`, coût de sortie d'astéroïde, Médias, Exploration II, visites et missions de déplacement) mais n'est pas comptée comme une sonde pour la limite, l'orbite et l'atterrissage (filtres `IN_SOLAR_SYSTEM`). Arrivée sur sa destination (Terre, ou Mars pour ET.4), la mission `GAIN_IF_SPECIMEN` se réclame en action gratuite : récompense de la carte + celle du spécimen, puis la capsule disparaît et le jeton devient le bonus de la première case libre de la piste bleue (`SpeciesSystem.placeSpecimenOnTrack`, appelé par `InteractionResolver.claimMissionRequirement`).
- **Fin de partie** : à la fin de la dernière manche, `TurnManager.endRound` appelle `ScoreManager.applyFinalScoring`, qui calcule les catégories (objectifs, cartes fin de partie, espèces, cartes Exertiens jouées), puis la pénalité de danger, et enregistre le détail dans `game.finalScores`. L'écran de fin (`EndGameModal`) le lit sans rien recalculer et désigne le ou les gagnants avec `ScoreManager.determineWinner`. Une fois en `FINAL_SCORING`, plus aucune action n'est acceptée (`ActionValidator`) et les robots attendent.
  - Conditions des cartes Exertiens : `END_CONDITION:<type>:<paramètre>:<seuil>:<PV>` dans `public/cards/exertiens.csv`, évaluées par `ScoreManager.revealExertienCards` (une seule fois par carte, FAQ Q45).
  - Danger : DANGER des cartes Exertiens jouées + danger des emplacements occupés par les marqueurs du joueur sur la piste Exertiens (`calculateExertienDanger`). Si les Exertiens sont découverts, le plus exposé (ex aequo compris) perd 10 % de son total arrondi à l'inférieur, après tous les autres PV. Aucune pénalité si personne n'a de danger positif.
  - Bonus des autres espèces (`calculateSpeciesBonuses`) : aucun selon les règles et la FAQ (seuls les Exertiens ajoutent une étape) ; les cartes Fin de partie des espèces (ET.5, ET.24 : `SCORE_PER_SPECIES_LIFETRACE`) sont décomptées avec les autres cartes Fin de partie.
- **Centauriens** : `player.centaurienMilestones` est une liste de `CentaurienMarker` (score, carte source éventuelle, `resolved` une fois atteint) qui restent affichés sur la piste de score. Palier du message de l'espèce : choix d'une tuile Message (`claimedBy` retient qui l'a prise). Palier d'une carte : effet « Réception » de la carte (`RECEPTION_REVENUE` ou `RECEPTION:<récompenses>` dans le CSV), sans choix (`SpeciesSystem.receiveCentaurienCard`).
- **Fenêtres et infobulles** : toute fenêtre de choix utilise `ui/modals/ChoiceModal` (`ChoiceModal`, `ChoiceOption`, `ChoiceFooterButton`), qui inclut le bouton « Voir le plateau » ; les choix de cartes de la main passent par `PassModal` (une carte : réservation, fin de manche) ou `CardPickModal` (plusieurs : défausse de fin de manche, défausse pour signaux, échange de 2 cartes), qui dessinent les cartes comme sur le plateau joueur (`ChoiceCardTile`, `CardContent`) avec l'attribut utile en surbrillance ; une option indisponible explique pourquoi dans son infobulle. Pas d'attribut HTML `title` : utiliser `setActiveTooltip` ou `components/HoverTooltip` pour garder l'aspect des infobulles du jeu (classe `.seti-tooltip`).
- **Historique** : le moteur rédige le message de chaque action (y compris orbite et atterrissage) puis ses conséquences avec le même `sequenceId` ; l'historique indente ces conséquences sous l'action.
- **Version** : `GAME_VERSION` (`core/version.ts`) = version de `package.json` (vérifié par `test/Version.test.ts`), affichée dans le menu et la documentation avec le commit du build (`__BUILD_COMMIT__`, injecté par Vite). Le serveur refuse un client d'une autre version mineure. L'augmenter à chaque version publiée.
- **Jeu à distance** : `GameRoom` (pur, `test/GameRoom.test.ts`) tient la partie d'une salle et passe par `GameSession` ; `server/GameServer.ts` (WebSocket `ws`, `test/GameServer.test.ts` avec de vrais clients) gère les connexions, le rythme des robots (1,5 s), l'enregistrement des salles et les vues (`viewFor`, `viewEntries`). Les cartes y sont lues sur disque (`DataLoader.setReader`). Le générateur aléatoire est global : `GameRoom` rétablit `game.rngState` avant chaque étape de robot, et crée les parties une à la fois. Premier joueur tiré au hasard (le message `create` accepte un `firstPlayer`, gardé par la sauvegarde de la salle, que l'interface n'envoie plus). Liste des salles : `GameRoom.summary`, `GameServer.listRooms`, `GET /rooms` (CORS des origines autorisées, `test/RoomList.test.ts`), lue par l'onglet Rejoindre. Annulation en ligne (`GameRoom.undo`, message `undo`, `test/OnlineUndo.test.ts`) : seulement les commandes du joueur pendant son tour en cours, tant que personne d'autre n'a joué (points d'annulation en mémoire, effacés par la commande d'un autre joueur, une étape de robot ou la fin du tour). Le jeu local n'utilise pas le serveur.
- **Client en ligne** : `session/RemoteClient.ts` (pur, `test/RemoteClient.test.ts` contre le vrai serveur : commandes et annulations avec accusé de réception `ack`, reconnexion automatique par le jeton, battement de cœur `ping`/`pong` qui détecte une connexion muette, `reconnectNow` au retour du réseau ou de la page, place perdue oubliée) ; `ui/hooks/useOnlineSession.ts` (place gardée dans `localStorage['seti_online']`), `ui/modals/OnlineModal.tsx` (créer, rejoindre, salon). Adresse du serveur : `__SERVER_URL__` injecté par Vite depuis `VITE_SERVER_URL` (en développement `ws://localhost:8787`), lu par `ui/serverUrl.ts` ; vide, le bouton « Partie en ligne » n'apparaît pas. Dans `BoardUI` : `run(command)` est **asynchrone** (en ligne, il se termine à l'accusé de réception ; une suite qui relit `gameRef` après une commande doit l'attendre avec `await`) ; `game` est la partie d'affichage, où les autres joueurs humains apparaissent comme robots (les composants désactivent alors les actions), `realGame` garde les vrais types (historique, écran de fin) ; une interaction d'un autre joueur n'est pas affichée (« En attente de … ») ; pas de robots locaux, de sauvegarde automatique ni d'outils de débogage en ligne ; l'annulation passe par le serveur (`online.state.undo`). Le nom du joueur (`ui/playerName.ts`, `localStorage['seti_player_name']`) est partagé par Nouvelle partie et Partie en ligne ; les deux fenêtres partagent leurs éléments (`ui/modals/SetupFields.tsx` : nom, liste des places `SeatList` avec niveaux et pastilles de couleur `PLAYER_COLORS`) et gardent le fond de l'accueil pendant une partie (`SpaceBackdrop overGame`). Au démarrage d'une partie (phase de mise en place, aucune carte réservée), `ui/components/FirstPlayerDraw` annonce le premier joueur déjà tiré par le moteur (radar), une fois par partie (clé : première entrée d'historique) ; les robots locaux attendent la fin. La partie solo (autosave) n'est jamais touchée par le jeu en ligne.
- **Effets d'une carte limités à son action** (Oumuamua) : la défausse de jetons (`GAIN_ON_TOKEN`, `GAIN_ON_TOKEN_AND_LAND` dans le CSV) est un effet de la carte (`DISCARD_TOKEN_FOR`, `DISCARD_TOKENS_THEN_LAND`), proposé par `DISCARDING_TOKEN` (`InteractionChoices.discardToken` : `repeat` tant qu'il reste des jetons, `then` gagné en arrêtant ; robots : `AIController.bestTokenDiscard`). Les gains par signal sur Oumuamua (`GAIN_ON_SIGNAL:oumuamua`, `GAIN_ON_FIRST_SIGNAL:oumuamua`) sont un buff actif `OUMUAMUA_SIGNAL_BONUS` portant le `sequenceId` de la carte, appliqué par `ScanSystem.performSignalAndCover`. Un `GAIN_ON_…` laissé en effet permanent devient un cercle de mission : `CardCatalog.test` vérifie que chaque type d'effet lu est traité par le moteur, `GAIN_ON_…` compris.  Les sauvegardes gardent les effets lus au lancement : la migration 2 → 3 de `GamePersistence` réécrit ceux de ces cartes.
- **Carte de fin de manche** : la pile de la manche est cachée (`viewFor`) jusqu'à la passe. `PassAction` défausse et marque la passe ; le joueur choisit ensuite sa carte pendant son tour (`CHOOSING_ROUND_CARD` avec son `playerId`, `InteractionChoices.chooseRoundCard`, nom privé dans l'historique ; robots : `AIController.bestRoundCard`), puis `PassAction.finishPass` passe au joueur suivant ou termine la manche. Sans pile, `PassAction` appelle `finishPass` aussitôt. La session met cette interaction en dernier (après celles de la rotation, sans menu d'ordre).
- **Premier joueur** : `GameFactory.setFirstPlayer(game, index)` fixe le premier joueur et les PV de départ dans l'ordre du tour (1 PV pour le premier, règles) ; `createGame` et `GameSetup.newGame` passent par elle.
- **Persistance** : `GamePersistence` (pur) + `useAutosave` (`localStorage['seti_autosave']`, écriture différée de 500 ms, immédiate si la page est quittée) + export/import JSON dans `SettingsModal`. Les sauvegardes portent `saveVersion` : tout changement incompatible du modèle incrémente `SAVE_VERSION` et ajoute une migration dans `MIGRATIONS` (appliquée aussi aux états d'annulation du journal). Une sauvegarde plus récente que le jeu est refusée (`SaveVersionError`). Elle enregistre aussi l'état du générateur aléatoire (`rngState`), rétabli au chargement.
- **Hasard** : jamais de `Math.random()` dans le moteur ni dans `ai/`, toujours `random()` de `core/random.ts` (générateur à graine). `GameFactory.createGame(noms, humainPremier, graine)` part de la graine (tirée au hasard si absente) et la note dans `game.seed` : même graine et mêmes choix = même partie. L'UI garde `Math.random` pour ce qui n'est pas du jeu (infobulles, noms des robots). Identifiants : `uniqueId()` de `core/ids.ts`, pas `Date.now()` seul.
- **Outils de débogage** : le `DebugPanel` n'est affiché que si la case « Outils de débogage » du menu Paramètres est cochée (`useDebugSetting`, `localStorage['seti_show_debug']`) ; la case et le panneau n'existent qu'en développement (`DEBUG_AVAILABLE`, `__DEBUG_TOOLS__` injecté par Vite), jamais dans la version publiée.
- **Style** : TS `strict`, `noUnusedLocals/Parameters`, `isolatedModules` (module ES, résolution `bundler` pour Vite ; `test/tsconfig.json` repasse en CommonJS pour Jest), `.editorconfig` (2 espaces, LF). Identifiants en anglais, commentaires et messages en français. Les valeurs d'enum sont des libellés FR affichés (`SectorType.YELLOW = "Jaune"`) et utilisés au parsing CSV : ne pas les modifier à la légère.
- **Tests** : Jest + ts-jest dans `test/`, type-checkés via `test/tsconfig.json` (inclus dans `npm run typecheck`).
  - `test/helpers/gameFixture.ts` : `createTestGame()` crée une **vraie** partie (fetch simulé qui sert `public/`, donc les vraies cartes ; graine fixe `TEST_SEED`, donc la même partie à chaque exécution), `makeCard()`, `getPlayer()`. À privilégier plutôt que des mocks d'état écrits à la main.
  - Un bug connu et pas encore corrigé est documenté par un `test.failing(...)`. Retirer `.failing` quand il est corrigé.
  - `CardCatalog.test.ts` vérifie toutes les cartes des CSV (effets lus et traités, jouées par un robot sans erreur) et que les robots gèrent toutes les interactions du moteur. Une nouvelle carte ou un nouvel effet doit le faire passer.
  - Couverture : SolarSystemPosition, ScanSystem, CardSystem (dont conditions de mission et défausse pour action gratuite), DataLoader (tous les CSV), TurnManager/PassAction, GameFactory, GameEngine, GamePersistence, InteractionResolver, InteractionChoices (chaque choix, côté joueur et robot), Anomalies, Exertiens, orbite/atterrissage, immutabilité, cardEffects, et des parties complètes entre robots (AITurn). `npm run test:coverage` : 100 % des instructions, lignes et fonctions du moteur (hors `ui/`), environ 91 % des branches, imposés par `coverageThreshold` (`jest.config.ts`) : une instruction non couverte se teste, ou se retire si elle est inatteignable (pas de `/* istanbul ignore */`) ; les cas limites et refus des sondes, du scan et des cartes ont leurs tests (`*EdgeCases.test.ts`). La géométrie du dessin (`ui/solarGeometry.ts` : `getSectorType`, `calculateObjectPosition`, `describeArc`) est hors du moteur et de la couverture.

## Hébergement

- **Interface (Netlify, offre gratuite)** : https://my-seti.netlify.app (origine autorisée par le serveur, `ALLOWED_ORIGINS` dans `render.yaml`) ; site statique, `netlify.toml` (`npm run build`, publie `dist/`). Rien de plus à faire pour le jeu solo. Netlify ne peut pas héberger le serveur WebSocket (fonctions de courte durée). Pour le jeu en ligne, définir `VITE_SERVER_URL=wss://…` (adresse du serveur, en `wss://` car le site est en HTTPS) dans les variables d'environnement de Netlify. Offre gratuite : environ 300 crédits par mois (environ 10 crédits par Go de bande passante, comptes créés depuis septembre 2025 ; 100 Go par mois pour les plus anciens) ; les PDF de `public/docs` (52 Mo) ne se téléchargent qu'au clic.
- **Serveur (Render, offre gratuite, choisi)** : `render.yaml` (Blueprint : `npm ci && npm run server:build`, `npm run server:start`, `/health`, `ALLOWED_ORIGINS=https://my-seti.netlify.app`). WebSocket pris en charge ; le service s'endort après 15 min sans trafic (HTTP ou message WebSocket) et met environ 1 min à se réveiller. **Disque non conservé** : les salles enregistrées sont perdues à chaque redémarrage ou redéploiement (Render peut redémarrer à tout moment) ; accepté pour l'instant. Pour des parties durables : disque persistant payant, ou enregistrer les salles dans une base gratuite (remplacer l'écriture des salles de `GameServer`).
